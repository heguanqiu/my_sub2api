# 最终需求清单 v4 细粒度节点计划

## 1. 文档目的

本文件用于把 [docs/requirements/final-requirements-v4.md](/home/heligong/Downloads/sub2api/docs/requirements/final-requirements-v4.md) 进一步拆解为可连续执行的细粒度节点，便于 agent 在多轮、不中断的前提下持续推进。

目标不是写出“大阶段”，而是把工作拆到：

- 单个节点职责明确
- 节点依赖清晰
- 节点完成后有可证明的验收结果
- 除支付/开票外，节点都可通过真实 API 调用完成验证

## 2. 全局执行规则

### 2.1 粒度规则

每个节点应尽量满足以下条件：

- 单节点尽量只覆盖一个核心能力
- 单节点改动不跨越过多业务域
- 单节点开发完成后能立刻验收
- 单节点失败时回滚成本低

### 2.2 验证规则

- 默认验证方式：真实 API 验证
- 不要求真实浏览器操作
- 支付与开票链路允许使用 mock/stub/sandbox 作为外部依赖替代
- 即使使用 mock/stub，系统内部状态变更仍需真实验证

### 2.3 通过标准

每个节点必须同时满足：

1. 代码改动完成
2. 对应 API 或状态行为可验证
3. 关键异常路径有最小覆盖
4. 不破坏现有主流程

## 4. 细粒度节点

## A1 角色常量与基础角色识别

- 依赖：无
- 目标：在后端和前端都支持 `sales` 角色的基础识别，不引入任何业务逻辑。
- 交付：
  - 角色常量扩展
  - 角色判断 helper 扩展
- 验收标准：
  - 系统能识别 `admin / sales / user`
  - 现有 `admin` / `user` 行为不变
- 验证方式：代码级 + 真实 API 辅助
- 验证要求：
  - 登录接口返回 `sales` 角色用户时，响应体可正确携带角色字段

## A2 用户归属字段入模

- 依赖：A1
- 目标：为 `users` 增加邀请归属和销售归属基础字段。
- 交付：
  - `invited_by_user_id`
  - `owner_sales_id`
  - 首充识别预留字段
- 验收标准：
  - schema 正确
  - migration 可生成
  - 现有用户读写不报错
- 验证方式：真实 API
- 验证要求：
  - 通过现有管理员用户查询接口，确认新字段不会导致接口报错

## A3 邀请链接表入模

## 6. Agent 运行建议

如果后续由 agent 连续执行，建议把单次工作单位控制在：

- 1 到 2 个连续节点
- 或 1 个节点 + 其真实验证

不建议一口气跨 Stage 并行开发，因为：

- 依赖链长
- 数据模型变更会放大回滚成本
- 权限和数据域问题容易在后期集中爆炸
