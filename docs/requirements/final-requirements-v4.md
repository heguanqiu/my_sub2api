# 最终需求清单 v4

## 1. 文档状态

- 状态：冻结版
- 用途：作为后续技术方案、计划拆分、节点安排的唯一需求基线
- 范围：源码改造后的原生实现，不采用外挂系统方案

## 2. 总目标

在现有 Sub2API 基础上，新增一套围绕邀请关系、销售归属、邀请奖励、受限数据视图、用户开票与百望云开票的业务能力。

本期只做：

- `admin / sales / user` 三层角色体系
- 邀请链与销售归属链
- 仅直接邀请人的首充一次性奖励
- 用户自己的充值记录与开票申请
- 销售查看自己归属范围内的用户、订单、开票
- 管理员归属调整与整棵子树迁移
- 百望云开票

本期不做：

- 销售返佣
- 多级邀请返佣
- 多级销售代理体系
- 外挂销售后台

## 3. 角色定义

### 3.1 管理员 admin

- 查看全量用户、订单、奖励、开票数据
- 创建和管理销售账号
- 修改邀请归属
- 修改销售归属
- 触发销售归属整棵子树迁移
- 管理开票失败重试、查看开票明细

### 3.2 销售 sales

- 只能查看自己归属范围内的用户
- 只能查看这些用户的充值记录
- 只能查看这些用户的开票记录
- 可以生成自己的邀请链接
- 不参与返佣结算
- 不能修改邀请归属
- 不能修改销售归属

### 3.3 普通用户 user

- 可以生成自己的邀请链接
- 可以邀请新用户
- 可以查看自己直接邀请的用户
- 可以查看自己的邀请奖励记录
- 可以查看自己的充值记录
- 可以基于自己的已支付订单申请开票

## 4. 关键业务规则

### 4.1 邀请归属

- 邀请归属只记录一级关系
- 使用字段：`invited_by_user_id`
- 只有管理员可以修改邀请归属

### 4.2 销售归属

- 销售归属使用字段：`owner_sales_id`
- 新用户注册时，默认继承邀请人的 `owner_sales_id`
- 如果邀请人没有销售归属，则新用户默认也没有销售归属
- 只有管理员可以修改销售归属

### 4.3 链式继承

如果：

- 销售 `S` 邀请用户 `A`
- `A` 邀请 `B`
- `B` 邀请 `C`

则：

- `A.owner_sales_id = S`
- `B.owner_sales_id = S`
- `C.owner_sales_id = S`

销售归属沿邀请链向下继承。

### 4.4 管理员修改邀请归属后的联动规则

- 管理员修改某用户的直属邀请人后
- 系统必须自动重算该用户整棵邀请子树的 `owner_sales_id`
- 不允许邀请链和销售归属链长期分叉

### 4.5 管理员修改销售归属后的联动规则

- 修改销售归属时，不是改单个用户
- 而是对子树整体迁移
- 影响范围包括：
  - 当前用户本人
  - 当前用户直接邀请的人
  - 这些人继续邀请的人
  - 递归到底

### 4.6 防环规则

- 禁止把用户改成自己的邀请人
- 禁止把用户挂到自己的后代节点下
- 所有邀请归属调整都必须做防环校验

## 5. 邀请链接规则

- 销售可生成邀请链接
- 普通用户也可生成邀请链接
- 邀请链接默认长期有效
- 邀请链接不自动过期
- 但系统应支持：
  - 手动禁用
  - 手动作废
  - 重新生成

建议主入口以邀请链接为主，不依赖手填邀请码。

## 6. 邀请奖励规则

### 6.1 奖励对象

- 只有直接邀请人可以获得奖励
- 不支持多级邀请奖励

### 6.2 奖励触发条件

- 被邀请用户首充成功后触发
- 仅触发一次

### 6.3 奖励类型

首版建议为余额奖励。

### 6.4 奖励冻结规则

- 同一个被邀请用户只能触发一次首充奖励
- 后续再充值不重复奖励

### 6.5 退款联动

- 如果首充订单退款
- 系统需支持邀请奖励冲回或作废

## 7. 订单与充值记录

### 7.1 用户充值记录

用户必须拥有自己的充值记录视图，用于：

- 查看历史支付订单
- 发起开票申请
- 查看订单支付状态

这部分不能只存在管理员视角。

### 7.2 订单快照

每笔订单建议固化如下快照字段：

- 下单用户 ID
- 下单时的 `owner_sales_id`
- 下单时的 `invited_by_user_id`
- 是否已触发邀请奖励
- 对应触发的奖励记录 ID（如有）

避免后续归属调整影响历史财务口径。

## 8. 销售可见范围

销售只能查看自己归属范围内的数据，至少包括：

- 名下用户列表
- 名下用户充值订单
- 名下用户开票记录

销售不能看到：

- 其他销售名下用户
- 全量邀请奖励数据
- 全量管理员页面

权限必须在后端落地，不能只依赖前端隐藏菜单。

## 9. 开票能力

### 9.1 用户侧

用户可对自己的已支付订单申请开票。

用户需具备：

- 发票资料管理
- 开票申请记录
- 发票结果查看

### 9.2 管理员侧

管理员可：

- 查看全部开票申请
- 查看开票失败原因
- 执行重试

### 9.3 销售侧

销售可查看自己归属客户的开票记录，但不可执行管理员操作。

## 10. 百望云开票

### 10.1 集成方式

- 对接百望云开票服务
- 推荐异步开票
- 不阻塞支付成功主链路
- 开票配置参数统一在系统设置中管理
- 配置形态参照现有支付配置接入方式
- 前端入口应进入现有系统设置页，而不是独立散落配置页

### 10.2 开票状态

至少包含以下状态：

- 待提交
- 提交中
- 已开票
- 开票失败
- 已作废/已红冲（预留）

### 10.3 开票记录

系统需记录：

- 百望云请求流水号
- 发票号
- 文件地址或文档记录
- 失败原因
- 重试次数

## 12. 后端能力要求

### 12.1 注册链路

所有注册入口必须统一支持：

- 解析邀请链接
- 写入 `invited_by_user_id`
- 继承 `owner_sales_id`

适用范围包括：

- 邮箱注册
- OAuth 注册
- 补全注册流程

### 12.2 邀请关系管理

需要后端支持：

- 查询直属邀请人
- 查询邀请子树
- 修改直属邀请人
- 子树销售归属重算

### 12.3 销售归属管理

需要后端支持：

- 修改单个用户销售归属作为根节点
- 对其整棵邀请子树批量迁移
- 预览迁移影响人数

### 12.4 邀请奖励处理

支付成功后需要：

- 判定是否属于首充
- 判定是否已发过奖励
- 生成邀请奖励流水
- 更新订单奖励状态

### 12.5 开票处理

需要支持：

- 创建开票申请
- 异步调用百望云
- 失败重试
- 用户查询自己的开票记录
- 销售查询归属客户的开票记录
- 管理员查看全量开票记录

## 16. 验证策略

### 16.1 总原则

- 除支付相关节点和开票相关节点外，所有功能都必须做真实 API 验证
- 真实 API 验证指：启动本地服务后，直接调用后端接口进行验证
- 不要求打开真实浏览器模拟用户行为
- 单元测试和集成测试可以作为补充，但不能替代真实 API 验证

### 16.2 支付与开票例外

- 支付链路允许使用现有支付测试路径、模拟回调、测试桩或本地伪上游完成验证
- 开票链路允许使用百望云适配层 mock / stub / sandbox 方式完成验证
- 但支付与开票的本地系统内状态流转仍需验证，例如：
  - 支付成功后订单状态变化
  - 开票申请状态变化
  - 重试状态变化

### 16.3 验收证据要求

- 每个开发节点必须给出至少一组真实 API 调用证据
- 证据应包括：
  - 请求入口
  - 关键响应字段
  - 关键状态变化
  - 如适用，数据库或后续查询结果的闭环验证

## 17. 验收标准

### 16.1 邀请链

- 用户注册成功后写入一级邀请关系
- 邀请链不会形成环

### 16.2 销售归属链

- 新用户正确继承邀请人的销售归属
- 修改邀请归属后，其子树销售归属正确重算
- 修改销售归属后，其子树整体迁移正确

### 16.3 邀请奖励

- 只有直接邀请人获得奖励
- 只有首充成功时触发
- 同一被邀请用户只奖励一次
- 首充退款后可正确冲回

### 16.4 用户充值记录

- 用户能看到自己的充值记录
- 用户能从自己的已支付订单发起开票

### 16.5 销售权限

- 销售只能看到自己归属范围内的数据
- 销售不能通过接口参数越权

### 16.6 开票

- 用户可申请开票
- 百望云开票异步可追踪
- 管理员可查看全量并重试
